## Why

The solution currently lives as a single `HackerRank1` WebAPI project in which controllers, EF `DbContext`, entities, DTOs, services, auth helpers, and migrations are all mixed together (inconsistent `LibraryService.WebAPI.*` vs `HackerRank1.*` namespaces). There are also two stale, near-duplicate test projects, and several required CRUD operations are still stubbed with `NotImplementedException`. The result is hard to reason about, hard to test, and does not follow classic .NET N-Layer (layered) best practices.

This change reorganizes by **technical responsibility** (Presentation → Business → Data Access → shared models), not by Clean Architecture’s inward dependency rule. That distinction matters for the lab: Clean and Vertical Slice will use different project layouts on their own branches.

## What Changes

- Reorganize the solution into distinct projects representing classic N-Layer responsibilities:
  - **Entities** — shared models (`Library`, `Book`), DTOs used across layers, and plain settings types that are not infrastructure-specific. No EF/framework package references.
  - **BusinessLogic (BLL)** — service interfaces + implementations, auth service, token generation. Orchestrates use cases; calls into Data Access.
  - **DataAccess (DAL)** — EF Core `DbContext`, repository interfaces + implementations, and migrations only.
  - **Api (Presentation)** — controllers, `Program.cs` / `Startup.cs` composition root, configuration binding, pipeline setup (JWT, CORS, Swagger).
- Align namespaces to their owning project (`LibraryService.Entities`, `LibraryService.BusinessLogic`, `LibraryService.DataAccess`, `LibraryService.Api`).
- Add a repository layer in Data Access; BusinessLogic services depend on Data Access repositories (dependencies flow **downward only**: Api → BusinessLogic → DataAccess → Entities). DataAccess must **not** reference BusinessLogic.
- Register all services/repositories via DI in the Api composition root.
- Consolidate the two duplicate integration-test projects into one test project targeting the Api project.
- Complete stubbed CRUD so the API remains **fully functional** after the restructure (library delete; book add/update/delete) while keeping the public HTTP contract unchanged.
- **BREAKING** project/assembly renames: `HackerRank1.csproj` is superseded by `LibraryService.Api`, and test projects are reconciled. Routes, payload shapes, and status codes remain unchanged (see specs).
- Keep the existing `InitialCreate` migration and Supabase schema intact (see Impact → migration-preservation and `design.md`).

## Impact

- **Code**: All files under `HackerRank1/` reorganized/moved into the new layer projects; `Startup.cs` rebuilt as composition root; controllers call BusinessLogic services via interfaces; services call DataAccess repositories.
- **APIs**: No change to public HTTP contract (routes, request/response JSON, status codes remain as documented). Methods currently throwing `NotImplementedException` are implemented per the documented contract (see specs). No new endpoints, no payload/status-code changes. **The app must build, test, migrate, and serve Swagger endpoints successfully after the migration.**
- **Dependencies**: Project references only downward — Api → BusinessLogic → DataAccess → Entities (Api may also reference Entities for binding/config types if needed; Api references DataAccess only as needed for DI registration of DbContext/repositories). Test project updated. NuGet packages re-scoped (e.g., EF/Npgsql live in DataAccess only).
- **Tests**: The two duplicate test projects merge into one that validates the Api still satisfies the HTTP contract.
- **Framework**: Stay on .NET 8 / EF Core 8 / Npgsql 8; no target-framework or package-version downgrade. This preserves the existing `InitialCreate` migration (generated by EF/Npgsql 8) exactly.
- **Credentials**: No Supabase password or other secrets are written into generated files, logs, commits, or docs. Existing `appsettings.Development.json` is referenced as config, never copied verbatim or echoed into any artifact.
